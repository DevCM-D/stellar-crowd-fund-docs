# Database Migrations

The platform uses Prisma Migrate for schema changes. All migrations are tracked as versioned SQL files and applied atomically.

---

## How Migrations Work

Prisma Migrate generates SQL migration files from changes to `backend/database/schema.prisma`. Each migration is a timestamped directory containing a `migration.sql` file:

```
backend/database/migrations/
├── 20250301120000_initial_schema/
│   └── migration.sql
├── 20250315093000_add_dispute_indexes/
│   └── migration.sql
└── 20250401150000_add_webhook_tables/
    └── migration.sql
```

A `_prisma_migrations` table in the database tracks which migrations have been applied.

## Local Development

### Create a migration

After editing `schema.prisma`:

```bash
cd backend
npx prisma migrate dev --name describe_the_change
```

This:
1. Generates the SQL migration file
2. Applies it to your local database
3. Regenerates the Prisma Client

Name migrations descriptively: `add_dispute_indexes`, `add_webhook_deliveries_table`, `add_reputation_events`.

### Reset the database

Drops all data and reapplies all migrations from scratch:

```bash
npx prisma migrate reset
```

Only use this in local development. Never run on a staging or production database.

### View migration status

```bash
npx prisma migrate status
```

Lists all migrations and whether each has been applied.

## Staging and Production

Use `migrate deploy` in automated pipelines — it applies pending migrations without generating new ones or resetting the database:

```bash
npx prisma migrate deploy
```

`migrate deploy` is safe for production:
- It applies only unapplied migrations, in order
- It does not generate new migrations
- It exits with a non-zero code if any migration fails, halting the deployment

Run it as part of your CI/CD pipeline, before starting the server:

```yaml
# Example: GitHub Actions
- name: Apply database migrations
  run: npx prisma migrate deploy
  env:
    DATABASE_URL: ${{ secrets.DATABASE_URL }}

- name: Start server
  run: npm start
```

---

## Migration Safety Rules

**Never edit a migration file after it has been applied to any database.**

If you need to undo a migration:
1. Write a new migration that reverses the change
2. Apply the new migration

If you need to fix a migration that was applied only in local dev:
1. `npx prisma migrate reset` (local only — destroys all data)
2. Fix the migration
3. `npx prisma migrate dev` to reapply

## Adding Indexes

When adding indexes to an existing table with large amounts of data, consider using `CREATE INDEX CONCURRENTLY` to avoid locking the table:

```sql
-- In the migration.sql file, replace the generated index:
-- CREATE INDEX ... (generated by Prisma)
-- with:
CREATE INDEX CONCURRENTLY "Escrow_tenantId_status_idx" ON "Escrow"("tenantId", "status");
```

The Prisma-generated migration will create the index with a table lock. For tables that need zero-downtime index creation, edit the migration file before applying.

---

## Backup Before Migrating

In production, always take a database backup before applying migrations:

```bash
pg_dump $DATABASE_URL > backup-$(date +%Y%m%d-%H%M%S).sql
```

Migrations that add columns or indexes are generally safe. Migrations that drop columns, rename columns, or change column types require more care — verify that no application code reads the old column before deploying.

---

## Prisma Client Regeneration

After any schema change, regenerate the Prisma Client:

```bash
npx prisma generate
```

In production, this typically happens as part of the Docker build step. Commit the schema file but not the generated client — the client is generated at build time.
